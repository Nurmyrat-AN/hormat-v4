# HORMAT-code-v4 — Exact Universal Media Upload Contract

## Owner clarification after this contract

The owner explicitly requested a universal **file** uploader accepting every format: no format allowlist or type-based rejection. No application size cap is enabled by default (`MEDIA_MAX_UPLOAD_BYTES=0`). Protocol requirements remain one multipart `file`, authentication, existing CSRF and no browser-supplied destination. Metadata discovery is best-effort and never rejects an unknown/malformed media type; unknown MIME is `application/octet-stream`, dimensions may be null. Original bytes are preserved.

Consequently `MEDIA_TYPE_NOT_ALLOWED` remains a reserved compatible code/client translation, not an active file-type restriction. `MEDIA_FILE_TOO_LARGE` applies only if the server operator explicitly configures a size cap. Public serving downloads non-raster content with safe headers; accepting a file does not authorize executing it in the browser.

Profile Basic Information was subsequently activated by explicit owner instruction; architecture section 31 and [CPANEL_PROFILE.md](CPANEL_PROFILE.md) supersede the temporary-only profile scope in original section 30. The upload/token contract remains unchanged.

The original exact contract follows unchanged below this clarification. See [MEDIA.md](MEDIA.md) for implementation and operational details.


Use the following as the exact V1 contract for the universal HORMAT CPanel media uploader.

This contract should be documented as a permanent HORMAT V4 infrastructure contract and used consistently by all future media-containing CPanel forms.

---

# 1. Upload endpoint

```http
POST /cpanel/media/upload
```

Requirements:

* authenticated CPanel session required;
* existing CSRF protection required;
* `multipart/form-data`;
* one file per request.

Multipart field name:

```text
file
```

Do NOT accept destination/domain information during temporary upload.

The upload endpoint's only responsibility is:

```text
receive
→ validate
→ store in cache
→ return temporary media reference
```

---

# 2. Request

Example conceptual request:

```text
POST /cpanel/media/upload

Content-Type: multipart/form-data

file=<binary>
```

Do not accept client-controlled parameters such as:

```text
destination
folder
path
userId
productId
finalFilename
```

Temporary upload is domain-independent.

---

# 3. Successful response

HTTP:

```text
201 Created
```

Response:

```json
{
  "success": true,
  "media": {
    "cacheToken": "01K5ABCDEF1234567890",
    "url": "/media/cache/01K5ABCDEF1234567890.webp",
    "originalName": "photo.jpg",
    "mimeType": "image/webp",
    "size": 184532,
    "width": 1200,
    "height": 1200
  }
}
```

`width` and `height` may be null for media types where they do not apply.

---

# 4. cacheToken is authoritative

This is critical.

Future forms submit:

```text
cacheToken
```

NOT:

```text
/media/cache/file.jpg
```

and NEVER:

```text
/var/hormat/media/cache/file.jpg
```

The browser-visible `url` exists only for:

* preview;
* `<img>`;
* other temporary presentation purposes.

The server must NEVER trust the returned URL as a filesystem reference during model Save.

---

# 5. cacheToken

`cacheToken` must be:

* generated by server;
* unique;
* opaque to client;
* safe for transport;
* impossible to use for path traversal.

UUID/ULID/secure random identifier are acceptable.

Example:

```text
01K5ABCDEF1234567890
```

The client should treat it as an opaque string.

---

# 6. Cache filename

Server controls physical filename.

Conceptually:

```text
MEDIA_ROOT/
  cache/
    <cacheToken>.<validated-extension>
```

Example:

```text
cache/
  01K5ABCDEF1234567890.webp
```

The original filename must NOT determine the filesystem path.

---

# 7. URL

The response:

```json
"url": "/media/cache/..."
```

is a browser-readable temporary preview URL.

It must never expose:

* filesystem root;
* absolute path;
* server directory structure outside public media namespace.

---

# 8. File metadata

Return:

```text
cacheToken
url
originalName
mimeType
size
width
height
```

Do not return unnecessary internal metadata.

If later video support requires:

```text
duration
```

we may extend the contract without breaking existing clients.

---

# 9. Do not transform original media yet

For V1, do not automatically resize/compress/convert uploaded media unless the current implementation genuinely requires it.

Preserve the validated uploaded media.

Therefore `mimeType` should represent the actual stored media type.

Image optimization/variants can be designed separately later.

---

# 10. Upload error contract

All expected upload failures should use the same structure:

```json
{
  "success": false,
  "error": {
    "code": "MEDIA_FILE_TOO_LARGE"
  }
}
```

Do not send translated text as the primary API contract.

The client maps `code` through our database-backed localization system.

---

# 11. Initial error codes

Support at least:

```text
MEDIA_FILE_REQUIRED
MEDIA_FILE_TOO_LARGE
MEDIA_TYPE_NOT_ALLOWED
MEDIA_FILE_INVALID
MEDIA_UPLOAD_FAILED
```

Authentication/CSRF infrastructure may continue using its existing error handling where appropriate.

Do not expose stack traces or filesystem errors.

---

# 12. Client uploader state

Every reusable media uploader instance should expose/maintain conceptually:

```js
{
    state: "idle",
    cacheToken: null,
    url: null,
    uploadPromise: null,
    error: null
}
```

Allowed states:

```text
idle
uploading
uploaded
error
```

---

# 13. Selection behavior

Immediately after:

```text
<input type="file">
```

changes:

```text
validate basic client constraints
        ↓
state = uploading
        ↓
POST /cpanel/media/upload
```

Do not wait for form Save.

---

# 14. Progress contract

Use real browser upload progress.

During upload expose:

```text
0..100
```

integer percentage.

Conceptually:

```text
state = uploading
progress = 0
...
progress = 47
...
progress = 100
state = uploaded
```

Do not fake progress.

---

# 15. Successful client state

After HTTP 201:

```js
{
    state: "uploaded",
    cacheToken: response.media.cacheToken,
    url: response.media.url,
    uploadPromise: null,
    error: null
}
```

The returned URL can immediately be used for preview.

---

# 16. Save contract

Every future form containing a universal uploader follows exactly this behavior.

## Case A — no new file

```text
state = idle
```

Submit model without a new media token.

Existing persisted media remains unchanged.

## Case B — upload complete

```text
state = uploaded
```

Submit:

```text
cacheToken
```

with the model request.

## Case C — upload running

```text
state = uploading
```

When Save is clicked:

```text
disable/prevent duplicate Save
        ↓
wait for uploadPromise
        ↓
if uploaded
        ↓
continue model Save automatically
```

The user should NOT need to press Save again.

## Case D — upload error

```text
state = error
```

Do NOT submit the model with the failed new media.

Show localized upload error.

Allow retry/reselection.

---

# 17. Domain Save request

A future domain request may conceptually contain:

```json
{
  "name": "Example",
  "avatarCacheToken": "01K5ABCDEF1234567890"
}
```

Exact field names belong to the consuming domain.

Examples may later be:

```text
avatarCacheToken
imageCacheToken
logoCacheToken
```

Do NOT send:

```text
avatarUrl: "/media/cache/..."
```

as the authoritative new-media input.

---

# 18. Finalization contract

Domain services call the Media Service internally.

Conceptually:

```ts
finalizeCachedMedia({
    cacheToken,
    destination
})
```

This is INTERNAL server code.

It is NOT a public browser endpoint.

The browser does not choose `destination`.

---

# 19. Trusted destination

Only trusted backend/domain code supplies destination.

Conceptually:

```text
profile service
→ users/avatar

product service
→ products

brand service
→ brands
```

Do NOT accept destination directly from request body.

---

# 20. Finalization result

Media Service returns conceptually:

```ts
{
    url: "/media/users/avatar/abc123.jpg"
}
```

It may internally return additional trusted metadata if needed, but consuming models primarily need the final URL.

---

# 21. Domain persistence

Correct flow:

```text
browser sends cacheToken
        ↓
domain validates request
        ↓
domain calls Media Service
        ↓
Media Service validates cacheToken
        ↓
cache file exists
        ↓
move/promote to trusted final directory
        ↓
final URL returned
        ↓
domain stores final URL in PostgreSQL
```

Never store the cache URL as permanent model media.

---

# 22. Cache token not found

If model Save references:

* invalid token;
* expired token;
* already finalized token;
* nonexistent token;

Media Service must reject it.

Conceptual internal error:

```text
MEDIA_CACHE_NOT_FOUND
```

Do not silently treat it as success.

---

# 23. One-time semantics

A successfully finalized cache token is consumed.

After successful promotion:

```text
cache file no longer exists
```

The same cache token should not be reusable for another model Save.

This prevents accidental repeated promotion.

---

# 24. Re-select contract

Suppose:

```text
A selected
→ A uploaded
→ cacheToken A

then

B selected
→ B uploaded
→ cacheToken B
```

The uploader's authoritative active token becomes:

```text
B
```

A must never be submitted by that uploader afterward.

A can be cleaned through temporary-upload cleanup.

---

# 25. Remove-new-selection contract

If user selects/uploads B and then clicks Remove before Save:

```text
active cacheToken = null
state = idle
```

If the model already had an existing permanent image:

```text
/media/users/avatar/old.jpg
```

it remains untouched.

Removing a NEW temporary selection does NOT mean:

`delete existing permanent media`.

Those are separate actions.

---

# 26. Existing media versus new media

Reusable uploader must distinguish:

```text
existingUrl
```

from:

```text
new cacheToken
new preview url
```

Conceptually:

```js
{
    existingUrl: "/media/users/avatar/current.jpg",

    state: "uploaded",
    cacheToken: "...",
    url: "/media/cache/new.jpg"
}
```

Before Save, preview may show new media.

If new selection is cancelled, return preview to:

`existingUrl`.

---

# 27. Cache cleanup contract

Cache media is temporary.

Configure TTL:

```env
MEDIA_CACHE_TTL_HOURS=24
```

or the project's chosen value.

Expired temporary uploads may be deleted automatically.

Therefore domain forms must never assume cache tokens are permanent.

---

# 28. Public media serving

Expose media through one controlled public URL namespace:

```text
/media/...
```

Filesystem root comes from:

```text
MEDIA_ROOT
```

Conceptually:

```text
MEDIA_ROOT=/data/hormat/media
```

maps to:

```text
/media/
```

Do not expose the configured filesystem path itself.

---

# 29. Security ownership

Because `/cpanel/media/upload` is authenticated, associate enough server-side context with temporary upload handling to prevent obvious cross-user abuse.

At minimum, a CPanel user should not be able to take another user's temporary upload token and finalize it accidentally/maliciously if ownership can be enforced cleanly.

Since we currently do NOT have a media database table, implement this without over-engineering.

A signed/opaque token or safe temporary metadata mechanism is acceptable.

If enforcing token ownership robustly requires a significant architectural change, report it before introducing a new database domain.

Do NOT create a media database table solely for this without explicit approval.

---

# 30. Profile integration

For the current `/cpanel/profile` avatar UI:

Selecting a file must now:

```text
select
→ immediate upload
→ progress %
→ cacheToken
→ preview
```

But Basic Information Save remains inactive in this task.

Therefore:

`cpanel_users.avatar_url`

must NOT change yet.

This task verifies the upload contract only.

---

# 31. Localization

Uploader UI uses database-backed localization.

API returns stable error codes such as:

```text
MEDIA_FILE_TOO_LARGE
```

Client maps them to translated UI messages.

All required UI messages must have real:

* tm
* ru
* en

database translations.

No hardcoded client translation dictionary.

---

# 32. Exact V1 summary

Permanent V1 contract:

```text
FILE SELECT
    ↓
POST /cpanel/media/upload
multipart field: file
    ↓
201
{
  success: true,
  media: {
    cacheToken,
    url,
    originalName,
    mimeType,
    size,
    width,
    height
  }
}
    ↓
client keeps cacheToken
    ↓
SAVE
    ↓
if uploading → WAIT
if uploaded → submit cacheToken
if error → BLOCK SAVE
if idle → no new media
    ↓
domain backend receives cacheToken
    ↓
Media Service finalizes to TRUSTED server-side destination
    ↓
returns final URL
    ↓
model stores final URL
```

This contract should be considered stable for HORMAT V4 unless explicitly revised later.

Document it in the permanent architecture documentation.
